§ 3 — HOW TO BUILD IT IN REAL LIFE

From CAD to balancing hardware

3.1 — MECHANICAL

The rig

  • Base & frame: acrylic base plate, four brass standoffs, a mid-plate for the electronics, and a top plate that carries the motor.
  • Motor: a high-torque, low-backlash DC motor (a NEMA-17-class geared motor or small planetary DC servo). Backlash here is death — the joint feels like a stiff spring in the hand during tuning.
  • Rotary arm (B, length lB): lightweight and rigid — carbon-fibre tube, 3D-printed PETG or aluminium. A yoke (two small side plates) at its tip holds the pendulum axle.
  • Pendulum (A, length lA): the same light-rigid philosophy; keep its inertia low (J{}_\varphi small) for a snappy response.
  • Bearings: ball bearings at O and S; the model neglects friction, so you should minimise it.

3.2 — ELECTRONICS

Brain & senses

  • Microcontroller: a Teensy 4.0/4.1 or ESP32 — you want fast floating point and hardware interrupts at a 200–500 Hz loop; a plain Uno struggles.
  • Motor driver: fast-switching H-bridge (BTS7960 or Cytron MD10C) for the high transient currents during swing-up.
  • Arm encoder (θ): on the motor shaft, ≥ 1000 PPR.
  • Pendulum encoder (φ): at joint S — the critical sensor; an optical encoder ≥ 2000 PPR so \dot{\varphi} stays usable.
  • Power: a supply that can deliver the swing-up transients without sagging.

3.3 — CONTROL ARCHITECTURE

The same FSM the simulator runs

Because the system is severely nonlinear, no single linear controller spans the whole state space. The simulator implements a finite-state machine — an energy-pumping swing-up outside the capture zone, and a balance controller inside it. Balance is a full-state LQR computed live from the linearization of §2.5. It is sign-corrected for the derivation's basis convention. 

// 200 Hz control loop, dt = 5 ms
void controlLoop() {
  readEncoders();                // hardware interrupts, quadrature
  dPhi = lpf(phi - phi_old, dt); // α ≈ 0.1–0.3
  if (abs(phi) < 0.30) {
    // BALANCE — full-state LQR
    torque = -K[0]*phi - K[1]*theta
           - K[2]*dPhi - K[3]*dTheta;
  } else {
    // SWING-UP — energy pump
    E = 0.5*Jphi*dPhi*dPhi
      + mA*g*lA/2*(cos(phi) - 1);
    torque = Mmax * sign(-E * dPhi * cos(phi));
    torque -= kArm * dTheta;     // anti wind-up
  }
  torque = constrain(torque, -Mmax, Mmax);
  setMotorPWM(torque);
}

3.4 — SOFTWARE STEPS

From raw ticks to torque

  1. Encoders via interrupts — never digitalRead in the loop. Convert ticks with \theta = (\text{ticks}/\text{PPR})\cdot 2\pi.
  2. Velocities by finite difference inside the fixed 5 ms loop, then a first-order low-pass \dot\varphi_{f} = \alpha \dot\varphi_{raw} + (1-\alpha)\dot\varphi_{f,old}, \alpha \approx 0.1{-}0.3.
  3. The control loop fires on a hardware timer; see the pseudocode (3.3).
  4. Direction sanity — apply a positive PWM and confirm the arm moves the way a positive M(t) means in your frame. If the motor fights the math, the pendulum will crash violently. (The simulator's sign convention: positive M spins the arm counterclockwise viewed from above.)

3.5 — TUNING, PHASE BY PHASE

Don't skip ahead

  1. Phase 1 — sensors. Verify φ → 0 when the pendulum is upright; verify arm direction vs torque sign.
  2. Phase 2 — inner loop. Hold the pendulum up by hand, kill the arm terms, raise K_{p,\varphi} until the arm fights your hand, then add K_{d,\varphi} until it feels like a smooth stiff spring.
  3. Phase 3 — outer loop. Add a small K_{p,\theta}: to move the arm left, the motor first jerks right to unbalance the pendulum, then chases it. Add K_{d,\theta} to damp the base swing. Pendulum gains stay an order of magnitude above arm gains.
  4. Phase 4 — swing-up. Increase k_E gradually. Too low: never reaches the top. Too high: overshoots with too much speed for the balance loop to catch.
  5. For LQR (this lab): keep \mb{Q} diagonal with q_\varphi \gg q_\theta (pendulum first), raise R to soften torque, and verify the closed loop holds against a hand-flick. The simulator recomputes \mb{K} live — try it in §4.
